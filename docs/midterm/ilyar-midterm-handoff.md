## 正式实验结论

性能结论固定引用10月23日数据，不用演示的3次计时替换正式测量。

| 纯解码 | 基线中位ms | Base中位ms | buffer中位ms | buffer加速比 |
| --- | ---: | ---: | ---: | ---: |
| Alice | 2.1271 | 2.0791 | 1.4008 | 1.518 |
| Pride | 9.1154 | 8.9525 | 6.0531 | 1.506 |

- 同机环境：i9-12900H，Windows，MSVC 19.44.35229，x64 Release。
- 每种情况预热3次、测量30次；2份文本×3版本×2种scope，共360条正式记录。
- 纯解码包含编号输出；排除文件读写、编码、建表、预分配、结果核对和字节还原。
- 第二种scope加入编号到字节的转换，仍排除磁盘读写；buffer加速比为1.494与1.486。
- 同scope加速比=基线中位耗时÷当前中位耗时。约1.5倍表示速度提高约50%，耗时减少约三分之一。
- Base独立收益小，暂不能认定稳定。未固定核心、频率及后台负载，只测两份文本，不能推广为普遍收益或直接比较原论文性能。
- 压缩负载比例不含码表和文件头；解码优化未改变编码输入，不将压缩比例归因于解码优化。

## 本人需要讲清的实现

1. 输入为码长列表和EncodedData；MSB first写位流，bit_count不含尾部补零，symbol_count是预期符号数。
2. Start用12位前缀给出候选长度，Limit配合下界和有效位检查确定码字。
3. `index = base_sym[length] + code - base_cwd[length]`，再读`symbols[index]`得到符号编号；索引不一定等于编号。
4. Base预先合并`base_sym - base_cwd`，简化索引计算；当前仍读base_cwd检查码字下界，不是完全删除原数组访问。
5. buffer一次装载64位窗口，按`floor(64 / max_length)`限制批量数量；码字边界仍顺序确定，没有使用AVX2。
6. 装载时检查字节范围，解码时检查剩余有效位，结束时核对输出数量。
7. ABCA→`0|10|11|0`→`010110`→`0x58`，有效6位，输出4个符号，补零不能当成额外A。
